# 910B3 MegaGDN 分卡复测与原生 Profiling

11 月 27 日，物理卡 0–3 跑严格 MegaGDN，卡 4–7 跑原生 GDN。两组使用 Qwen3.8-27B BF16、TP4、MRV2、DSpark-7、eager、`gpu_memory_utilization=0.85`，最大长度 16,384，调度上限 4,096 token 和 32 条序列，关闭 Prefix Cache。vLLM Ascend 使用 `658e5fbdf`，Mega vendor 使用 `44e774a`。

### 128 token、并发 32

原矩阵 p50 从 1,272.8 ms 降至 908.6 ms。额外做了 12 轮，每组 384 条请求，换算后的汇总 p50 为 1,085.4 → 1,025.8 ms（−5.49%），p95 为 1,266.2 → 1,045.5 ms（−17.43%）。有 11 轮 Mega p50 更低。第 7 轮原生为 694.5 ms、Mega 为 1,028.6 ms，复现了单轮 +48.10%。原生和 Mega 在该轮分别有 4 和 5 个引擎迭代，迭代计数涵盖 prefill 与 decode。在 12 轮中，Mega 的引擎平均 prefill 时间从原生的 696.3 ms 降至 619.9 ms。Mega 每轮 p50 分成约 686–696 ms 和 1,029–1,046 ms 两组，分别伴随 3 次和 5 次迭代。这里能确认轮次波动与批次推进有关，两组迭代数包含 decode，单凭该计数无法定位第一批请求的切分位置。[12 轮逐请求样本和引擎指标](focus.json)

128 token、并发 16 的四轮分布同样有明显波动。该点的 p50 上升 66.4%，p95 由 1,101.3 降至 1,027.0 ms。

## 原生 Profiling 归因

用 vLLM `/start_profile` 和 `/stop_profile` 为两组各采了 128×32、4,096×1 和 12,288×1。每次采集覆盖 4 个 TP rank，共 24 份。使用安装版 TorchNPU profiler 的 CPU + NPU Level1 数据，离线调用 `torch_npu.profiler.profiler.analyse`，验证每份都有正常停止记录、`trace_view.json` 和 `kernel_details.csv`。仅启用 vLLM 自带的 profiler，前端请求计时由压测客户端记录。[采集索引](profile_index.md)

### 主核接近两倍速，直接节省的整网时间约为 5–6%

4,096 token 单请求，两边都按 `4090 + 6` 分两次 prefill。12,288 token 单请求，两边都按 `4090 × 3 + 18` 分四次。按客户端发请求到首 token 的窗口裁剪，每个 rank 上累计 GDN 主核设备耗时，再取 4 个 rank 的中位数。这个窗口用于归因，正式 TTFT 统计来自 profiler 关闭时的独立请求。

| 单请求输入 | 原生 GDN 主核（ms） | Mega 主核（ms） | 主核节省 / 原生首字窗口 | 采集中的原生 → Mega 首字（ms） |
| --- | ---: | ---: | ---: | ---: |
| 4,096 | 90.82 | 46.24 | 44.58 ms / 5.20% | 856.54 → 808.73 |
| 12,288 | 244.81 | 130.95 | 113.87 ms / 5.81% | 1,959.38 → 1,829.73 |

原生 GDN 主核仅占上述首字窗口的 10.60% 和 12.49%。12,288 token 的 Mega rank 0 中，矩阵乘设备累计约 624 ms，CANN 报告的非重叠通信约 512 ms，主核约 129 ms。rank 0 的这些量级解释了主核接近两倍速时，整网依然只省几十到一百多毫秒。表中主核节省除以首字窗口用于说明量级，通信、计算和下发存在依赖及重叠关系。[24 份 trace 的统计](profile-summary.json)

### 融合主核之外的状态准备和下发仍存在

12,288 token 的 rank 0 中，原生和 Mega 在 `vllm::qwen_gdn_attention_core` 的 Host 累计范围为 463.40 ms 和 464.73 ms。这个范围含嵌套调用和下发，和设备耗时不能相加。Mega 减少了 `contiguous` 调用，但仍通过旧的 12 输出绑定返回中间量。绑定每次为 A、FP32 逆矩阵、低精度逆矩阵、分块状态和末状态执行 5 次 `zeros`。192 次 Mega 调用对应 960 次 `aten::zeros`，累计 Host 范围约 19.83 ms。96 次调用的 4,096 token 用例对应 480 次和 9.52 ms。[绑定源码](https://github.com/singzhou/xllm-ops/blob/44e774aca24cf474eaf99f9840e7ad9df42929c5/test/python_test/RegisterOps.cpp) · [24 份 trace 的统计](profile-summary.json)

长请求的 Mega GDN 范围内还可见 `aten::item`。4,096 和 12,288 token 中分别有 96 和 192 次，全都位于尾部输出缩放 `aten::mul_` 内，最长 5 µs。逐个检查这些范围，未观察到重叠的 ACL Stream/Event 同步或 DeviceToHost 搬运。这与适配器用 Python 标量做 `out.mul_` 的路径一致。[标量调用核对](scalar-scope-validation.json)

### 128×32 的批次切分随轮次变化

这次 stock trace 中，原生的主核输入是两批各 128 token，再加 2,432 和 1,408 token，共 4 次 prefill。Mega 是两批各 128 token，再加 3,840 token，共 3 次。两边输入共 4,096 token，单个 forward 的请求数分布不同。此采样中主核累计为 102.66 → 50.45 ms，约节省原生首字窗口的 3%。因为切分不同，这两个累计值同时反映算子和批次差异。补测中的单轮 +48.1% 与此采样不是同一轮。现有证据能解释短请求 p50 为什么对批次推进敏感，无法从这一次采样确定产生切分差异的具体事件。[128×32 采集窗口及输入形状](profile-summary.json) · [12 轮补测](focus.json)
